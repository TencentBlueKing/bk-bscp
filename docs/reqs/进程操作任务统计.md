## 一、需求背景与目标

进程操作（启动 / 停止 / 重启 / 重载 / 强杀 / 托管 / 取消托管 / 更新托管 / 清除）与配置文件下发通过异步任务框架执行，执行结果落在任务框架的三张表中。批次详情页只能看到单个批次的五态统计与失败列表，缺少：

- 跨批次、跨时间范围的成败趋势与失败原因分布；
- 错误码维度的聚合与下钻；
- 按人员、按业务维度的失败分布；
- 与概览一致口径的失败明细列表。

本方案目标：

1. 在不改动任务框架表结构的前提下，基于 `task_batches` + `task_records` 给出**口径明确、可下钻、性能可控**的统计实现；
2. 建立**错误码归因**：写侧用 `pkg/taskerr` 把能拿到的真实错误码写进 `message` 的结构化段，读侧解析聚合；
3. 提供**跨业务（平台级）统计视图**，不按单业务隔离、不判断用户业务权限（见 5.5）。

> 说明：本文档按当前代码回写。原型 `docs/reqs/进程操作任务统计-原型.html` 不在同步范围，页面字段以 5.3 的接口契约为准。

## 二、现状与数据模型

### 2.1 三层结构与标识

```
task_batches         1 行      id = batch_id
  └── task_records   N 行      每行 = 一个进程实例的一次操作
        │                     task_index = "<batch_id>"，task_index_type = 'task_batch'
        │                     task_id = UUID（全局唯一）
        └── task_step_records  4 行/任务   (task_id, name) 联合唯一
```

进程操作任务的 4 个固定步骤：

| # | `task_step_records.name` | 职责 |
|---|---|---|
| 1 | `CompareWithCMDBProcessInfo` | 对比 DB 配置与 CMDB 最新快照 |
| 2 | `ValidateOperateProcess` | 操作合法性校验（属性矩阵 + 状态类校验） |
| 3 | `OperateProcess` | 调 GSE 执行 |
| 4 | `FinalizeOperateProcess` | 回写进程实例状态 |

清除进程、更新托管任务的步骤名不同（`DeleteValidateOperateStep`、`ValidateOperateStep` 等），但结构与粒度一致。

### 2.2 可用字段盘点

| 统计所需信息 | 实际落点 | 可用性 |
|---|---|---|
| 业务 ID / 租户 | `task_batches.biz_id` / `tenant_id` | ✅ 索引 `idx_tenantID_bizID_ccProcessID(tenant_id, biz_id)` |
| 任务对象 / 操作类型 | `task_batches.task_object` / `task_action` | ✅ 统计按 `task_object` 过滤 |
| 批次状态 | `task_batches.status` | ✅ |
| 批次创建时间 | `task_batches.created_at` | ✅ 统计的时间口径（见 3.2） |
| 任务状态 | `task_records.status` | ✅ `idx_status` |
| 创建人 | `task_records.creator` | ✅ |
| 任务开始/结束/耗时 | `task_records.start / end / execution_time` | ✅ |
| 错误码 | `task_records.message` 的 `[BSCP-ERR]` 结构段（新数据）；历史数据回退 `errorCode=(\d+)` 文本 | ✅ 已改造写入，见 3.4 |
| CC 进程 ID | `task_records.common_payload.ProcessPayload.CcProcessID` | ⚠️ JSON，只用于明细展示 |
| 进程实例 ID | 表内无独立列（任务与实例 1:1） | ❌ 明细改展示 CC 进程 ID |
| 业务名称 | 无（仅 `biz_id`） | ⚠️ 跨业务视图外部映射：`cmdb.ListAllBusiness` 拉全量 `bk_biz_id → bk_biz_name` 后内存回填，见 5.2 |

> 说明：`common_payload` 随 `task_records` 一行返回、无需 join，但其中 `ConfigData` 为进程配置快照（数 KB~十几 KB）。聚合查询刻意只 `SELECT task_index, message, creator`，不为取 CC 进程 ID 扫这一列；`common_payload` 只在明细分页命中的行上读取。

### 2.3 已核实的关键事实（口径依据）

1. **步骤行在任务创建时一次性写入**。框架 `CreateTask` 在一个事务内插入 1 条 `task_records` + N 条 `task_step_records`，步骤初始状态为 `NOTSTARTED`，不是"执行到哪步才写哪条"。
2. **失败不新增行**。框架 `UpdateTask` 对步骤按 `task_id + name` 做 `UPDATE`；数据库层有 `(task_id, name)` 联合唯一索引兜底。
3. **步骤串行执行、失败即中断**。四个步骤均未设置 `SkipOnFailed`，某步失败后任务直接置 `FAILURE`，后续步骤保持 `NOTSTARTED`，**一个任务通常最多只有 1 个失败步骤**。
4. **任务与实例是 1:1**。`OperateTask` 构造时只接收一个实例标识，即"一次进程操作任务 = 一个进程实例"。因此"任务数"与"实例数"在数值上恒等。
5. **重试覆盖历史**。任务级重试（`RetryGroup`）复用同一 `task_id`，会把所有步骤重置为 `NOTSTARTED`、清空 `message`、`retry_count = 0`。**重试前的失败原因与错误码无法从表内还原**。
6. **错误码有两条来源，都在 `message` 里**：
   - 新数据：`pkg/taskerr` 写入的双哨兵结构段 `[BSCP-ERR]{"code":...,"msg":"..."}[/BSCP-ERR]`，**置于错误文本最前面**；
   - 历史数据：自由文本 `... errorCode=791001, errorMsg=...`，读侧用正则兜底。
7. **维度全在 JSON 里**。`task_step_records.payload` / `task_records.common_payload` 由 `json.Marshal` 生成且结构体无 json tag，key 为 PascalCase（`$.CcProcessID`、`$.BizID` 等），列为 `mediumtext`，**无法建索引**。
8. **框架表不可加列**。本地 `internal/task/table.go` 的 `Record` / `StepRecord` 必须与框架 `mysqlstore` 定义完全一致（只有 `payload` / `common_payload` 允许放大为 `mediumtext`），由测试强校验：

```131:134:internal/task/table_test.go
func TestStepRecordAlignedWithFramework(t *testing.T) {
	assertSchemaAligned(t, &StepRecord{}, &mysqlstore.StepRecord{})
}
```

> 结论：任何"给任务框架表加业务列"的方案都不可行（除非 fork 框架），统计只能在读取侧聚合。

### 2.4 状态枚举全集

| 层级 | 取值 |
|---|---|
| `task_batches.status` | `running`、`succeed`、`failed`、`partly_failed` |
| `task_records.status` | `INITIALIZING`、`RUNNING`、`SUCCESS`、`FAILURE`、`TIMEOUT`、`REVOKED`、`IGNORED`、`NOTSTARTED` |
| `task_step_records.status` | `NOTSTARTED`、`RUNNING`、`SUCCESS`、`FAILURE`、`IGNORED` |

说明：

- `IGNORED` 是 BSCP 引入的框架终态，用于 GSE 幂等错误码 **828 重复启动 / 829 无需停止**，语义是"目标态已达成"，视同成功但计入独立分类；
- 参与统计的批次状态只有 `succeed` / `failed` / `partly_failed`（见 `finishedBatchStatuses`），`running` 批次整体不进入统计；
- 终态批次内仍可能有残留的 `INITIALIZING` / `RUNNING` / `NOTSTARTED` 任务，概览通过 `running` / `not_started` 单列展示，**不计入失败**。

## 三、统计口径定义（本文档的核心）

### 3.1 指标定义

以"任务"为统计单元（= 一个实例的一次操作），步骤只用于失败原因展示。

统计范围（`cmd/data-service/service/task_statistics.go`）：

```
task_batches: tenant_id 命中当前租户
          AND task_object IN ('process','config_file')
          AND status IN ('succeed','failed','partly_failed')
          AND created_at BETWEEN [start, end]
          [AND creator IN (creators...)]
task_records: task_index IN (批次 ID) AND task_index_type = 'task_batch'
```

| 指标 | 定义 | 数据来源 |
|---|---|---|
| 执行实例总数 `total` | 时间窗内上述批次的 `task_records` 行数（**含所有状态**） | `task_records` 计数 |
| 成功实例数 `success` | `status = 'SUCCESS'` | 同上 |
| 幂等忽略实例数 `ignored` | `status = 'IGNORED'` | 同上 |
| 未执行实例数 `not_started` | `status = 'NOTSTARTED'` | 同上 |
| 运行中实例数 `running` | `status IN ('INITIALIZING','RUNNING')` | 同上 |
| 执行失败实例数 `failed` | `total - success - ignored - running - not_started` | 计算值 |
| 失败率 `failure_rate` | `failed / total`，`total = 0` 时为 0 | 计算值 |
| 错误码分布 `error_codes` | 失败记录按错误码分组计数，Top 10 + "其他" | `task_records.message` 解析 |
| 人员失败分布 `creators` | 失败记录按 `creator` 分组，Top 3 + "其他"；空创建人归 `-` | `task_records.creator` |
| 业务失败分布 `businesses` | 失败记录按批次 `biz_id` 分组，Top 5 + "其他" | 批次 `biz_id` + CMDB 业务名 |

强制等式（由 `buildStatisticsOverview` 保证）：

```
total = success + ignored + failed + running + not_started
```

> 注：错误码分布的桶之和 **可能小于** `failed`，因为取不到错误码（含 `code = 0`）的失败不进分布。

### 3.2 三层计数的换算与去重

| 层级 | 计数方式 | 关系 |
|---|---|---|
| 批次 | `COUNT(*)` on `task_batches` | 与其余两层无固定倍数关系 |
| 任务 / 实例 | `COUNT(*)` on `task_records` | 1:1 |
| 步骤 | `COUNT(*)` on `task_step_records` | 每任务固定 4 行；**本期统计不读取该表** |

强制规则：

- 失败实例数**必须**在任务层去重，禁止用 `COUNT(step WHERE status='FAILURE')` 代替。
- **`task_batches.total_count` 不等于 `task_records` 行数**：`total_count` 是"应下发实例数"，任务构建 / `DispatchGroup` 失败时批次已创建但任务行不存在，差额由 `AddFailedCount` 计入批次 `failed_count`。统计的实例总数与失败数一律用 `task_records` 计数，`total_count` 只用于批次列表展示。
- **时间口径统一按 `task_batches.created_at`**：批次侧过滤时间窗，任务侧不再按时间二次过滤。原因有两条：批次的 `start_at` / `end_at` 只在任务真正开始执行后才写入，用它过滤会漏掉"已创建未开始"的批次；任务的 `start` 对未执行任务为空值，按它过滤会把未执行任务整体排除。明细排序用 `task_records.created_at DESC, id DESC`。
- 一次统计内部是**两次独立查询**（状态计数 + 失败聚合），不是同一数据库快照，并发写入时概览与图表可能存在少量偏差，按最终一致处理（代码注释已声明）。
- 统计链路显式过滤 `task_records.deleted_at IS NULL`：状态计数扫描到自定义结构体时 GORM 不会自动注入软删除条件，必须手写，否则已删除记录会被算进总数。

### 3.3 失败判定

**一句话：成功、幂等忽略、未开始、运行中之外的状态一律算失败。**

判定用的是排除法（`nonFailedStatuses`）：

```go
nonFailedStatuses = []string{"SUCCESS", "IGNORED", "INITIALIZING", "RUNNING", "NOTSTARTED"}
```

1. **是否失败**：`task_records.status NOT IN ('SUCCESS','IGNORED','INITIALIZING','RUNNING','NOTSTARTED')`。命中 `FAILURE`、`TIMEOUT`、`REVOKED` 以及任何未知状态。
2. **取码**：失败记录解析 `message` 中的 `[BSCP-ERR]` 段取 `code`；没有结构段时回退正则 `errorCode=(-?\d+)`；仍取不到返回 0（0 表示"没有错误码"，不是真实错误码）。
3. **失败步骤**：只用于明细展示，不参与计数；一个任务只计 1 次。
4. **统计范围**：只统计**所属批次已终态**的任务。批次未终态时整体不进入统计，避免运行中任务按"非成功即失败"被计入，导致失败数随查询时刻跳变。

### 3.4 失败归因模型（错误码）

#### 3.4.0 两条原则

1. **写侧只记录能拿到的真实错误码**，不为归因编造码；拿不到码就不写结构段；
2. **读侧不从文本推断错误码**，只提取 `code` 做聚合；`msg` 只用于展示。

```
failure
└── code   错误码 ──> BSCP 自有码（4100500 / 4100501 / 4103003）/ 外部平台原始码 / 无码
```

#### 3.4.1 错误码表

| 码 | 常量 | 含义 |
|---|---|---|
| `4100500` | `taskerr.CodeProcessMismatch` | 执行的进程与实际绑定的业务信息不匹配，建议执行前先核对进程配置信息与 CMDB |
| `4100501` | `taskerr.CodeProcessCmdNotConfigured` | 操作所需的命令未配置（`start_cmd` / `stop_cmd` 等为空），进程配置不完整 |
| `4103003` | `taskerr.CodeProcessStageBlocked` | 优先级级联阻断：优先级等于 `[N]` 的进程操作已失败，后续优先级阶段不再执行（该任务本身未执行） |
| 其他非 0 码 | — | GSE 返回的原始码，原样透传（如 `1015000`、`1015012`、`791001`、`828`、`829`） |
| 无码 / `0` | — | DB 失败、payload / JSON 解析、参数构建、任务框架、脚本已执行失败、GSE 网络失败 / 轮询耗尽等 |

关键约束：

- **`4100500` 不是通用兜底码**，只表示"进程与业务信息不匹配"；DB 失败、参数构建失败、框架缺陷等自身问题**不写码**；
- 不为 GSE / CMDB 交互失败定义占位码，没有真实返回码时保持无码；
- GSE 执行类结果码原样记录，不映射成 BSCP 码。

#### 3.4.2 写入链路

进程操作链路（`internal/task/executor/process`）：

| 错误产生位置 | 记录 |
|---|---|
| DB 配置与 CMDB 快照不一致、快照缺失 | `4100500` |
| 命令未配置（stop / start / 其他缺失项） | `4100501` |
| 优先级级联阻断 | `4103003`（`internal/task/priority/stages.go`） |
| GSE 返回结果码 `procResult.ErrorCode != 0` | 透传原始码 |
| 接口调用失败（网络 / 连接中断）、轮询耗尽、结果 key 缺失、结构异常 | 无码 |
| 结果码 `828` / `829` | 任务置 `IGNORED`，不计失败 |
| 结果码 `115` | 未终态，不计失败；轮询耗尽按无码处理 |
| 属性矩阵 / 状态校验拦截、payload 解析、参数构建、DB 失败 | 无码 |

配置下发 / 检查链路（`config_push.go` / `config_check.go`）：`taskerr.New(int32(r.ErrorCode), WithMsg(r.ErrorMsg))`，`ErrorCode` 为 0 时写入 `code: 0`（读侧不进分布），非 0 时透传。

#### 3.4.3 结构段协议

```text
[BSCP-ERR]{"code":4100500,"msg":"compare process config failed"}[/BSCP-ERR]
```

框架写入后的完整形态：

```text
step OperateProcess running failed, err=[BSCP-ERR]{"code":4100500,"msg":"..."}[/BSCP-ERR] 进程启动失败, retried=1, maxRetries=3
```

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `code` | int | 是 | 见 3.4.1；`omitempty` 不生效，0 也会写出 |
| `msg` | string | 否 | 错误摘要，写入前按 **8192 字节**截断（`maxMsgLen`），UTF-8 边界安全 |

约束：

- 结构段**置于错误文本最前面**：`task_records.message` 为 `text`（65535 字节），超长时 MySQL 静默截断尾部，段在前保证归因不丢；
- `msg` 内的哨兵字符会被移除（`sanitize`），避免提前闭合结构段；
- 使用 `json.Encoder` + `SetEscapeHTML(false)`，中文不转义、不产生字节膨胀；
- 读侧 `Decode` 用起止双哨兵截取，**未知字段被忽略**，因此历史上带 `src` / `err_code` 的数据可正常读到 `code`；
- 解析失败不报错、不丢行，按无码处理；
- 步骤配置了 `MaxRetries` 时框架会在 err 后追加 `, retried=N, maxRetries=M`，展示侧会转成「（已重试 N/M 次）」。

#### 3.4.4 展示侧文本处理（`taskerr.Readable`）

失败明细的 `failed_reason` 与批次详情的 `message` 都走同一套处理：

1. 剥离 `[BSCP-ERR]...[/BSCP-ERR]` 结构段；
2. 剥离框架前缀 `task <name> / step <name> running failed, err=`；
3. 末尾 `retried=N, maxRetries=M` 转为「（已重试 N/M 次）」；
4. 剥离后为空时回退到结构段的 `msg`；
5. 明细侧再按 **rune** 截断到 500 字符（避免切断中文）。

#### 3.4.5 无码与框架写入边界

| 场景 | message | 结果 |
|---|---|---|
| 任务超时 | `task exec timeout` | 计失败，无错误码 |
| 任务 revoke | `task has been revoked` | 计失败，无错误码 |
| 步骤 panic | 框架文本 | 计失败，无错误码 |
| 批次级联阻断 | 框架 `BlockMessage`（新数据由 `4103003` 携带） | 任务 `INITIALIZING` 时不计失败 |
| 改造前历史数据 | 无结构段，可能有 `errorCode=` 文本 | 有则提取，无则不计入分布 |

#### 3.4.6 错误码统计口径

| 规则 | 值 |
|---|---|
| 统计单元 | 任务（1 任务 = 1 实例），不是步骤 |
| 时间范围 | 单次查询跨度 ≤ 31 天；未传时默认最近 7 天 |
| 统计范围 | 见 3.1 |
| 批次上限 | `maxStatisticsBatches = 50000`，超出**直接报错**要求收窄时间范围（不截断） |
| 人员上限 | `maxStatisticsCreators = 500`，超出报错 |
| 分批查询 | 批次 ID 按 `statisticsBatchChunk = 250` 一组分片 |
| 单批扫描上限 | `statisticsFailureRowLimit = 120000` 条失败记录，超出时该片分布可能偏少并打日志，其余分片继续统计 |
| 一条失败只贡献 1 个码 | 取 `message` 的 `code`，不因步骤数或重试次数放大 |
| 无码任务 | 计入 `failed`，**不进入错误码分布**（不生成 `0` 的桶） |
| TopN | 错误码 10、人员 3、业务 5，超出合并为 `key="other"`、`name="其他"` |
| 排序 | 数量降序；数量相同时按 key 升序，保证结果稳定 |
| 禁止 | 读侧按 `msg` 文本推断错误码 |

### 3.5 重试口径

| 场景 | 处理 |
|---|---|
| 任务级重试（批次详情"重试失败任务"） | 复用同一 `task_id`，表中只有最终结果；统计反映"最终结果"，不重复计数 |
| 用户重新发起操作（新批次） | 新 `task_id`，计为一次新任务 |

**UI 文案需注明**：统计为"最终执行结果"，不包含重试前的失败尝试（历史尝试只存在于日志）。

### 3.6 时间与批量口径

- 默认时间范围：最近 **7 天**（`defaultStatisticsRange`）；
- 最大跨度：**31 天**（`maxStatisticsRange`），超出返回 `InvalidParameter`；
- 只传一端时自动补齐另一端，并把补齐后的跨度限制在 31 天内；
- `time_range_end < time_range_start` 返回 `InvalidParameter`；
- 批次数量上限 **50000**，超出返回 `InvalidParameter`，提示收窄时间范围；
- 人员多选上限 **500**，超出返回 `InvalidParameter`。

## 五、实现方案

### 5.1 方案选型

| 方案 | 做法 | 结论 |
|---|---|---|
| **A message 结构化 + 读侧聚合（本期）** | 步骤统一返回 `taskerr` 结构化错误，由框架写入 `task_records.message`；统计只查 `task_batches` + `task_records`，Go 侧解析聚合 | ✅ 已落地，不改框架表 |
| **A2 跨业务视图（本期）** | 复用 A 的解析聚合，DAO 只按租户 + 时间 + 人员过滤，另加业务名映射与按 `biz_id` 分组 | ✅ 已落地 |

### 5.2 查询链路

**概览 + 图表（`TaskStatistics`，一次请求内完成）：**

```
① task_batches  →  TaskBatch().ListRefs(kt, filter, nil, maxBatches+1)
                   过滤：tenant_id / task_object IN (process,config_file)
                         / status IN (succeed,failed,partly_failed)
                         / created_at 窗口 / creator IN (creators)
                   SELECT id, biz_id, created_at   ORDER BY id DESC
                   → batchRefs（用于 batch_ids 与 biz_id 映射，不做截断）
② task_records  →  分片（250/片）两次查询：
                   ②-1 StatusCount：GROUP BY status（只用于概览）
                   ②-2 ListForStatistics：SELECT task_index, message, creator
                        WHERE status NOT IN (成功/忽略/未开始/运行中)
                        ORDER BY created_at DESC, id DESC  LIMIT 120000
③ Go 侧         →  解析 message 取 code（结构段优先，正则兜底）
④ 内存聚合      →  error_codes / creators / businessCounts（按 task_index 累加）
⑤ 业务名回填    →  biz_id 经 ListRefs 映射回业务，再调 cmdb.ListAllBusiness 取名称
                   失败降级为 biz_id 字符串
```

**失败明细（`TaskFailureTasks`）：**

```
task_batches AS b  JOIN  task_records AS r
  ON r.task_index = CAST(b.id AS CHAR) COLLATE utf8mb4_unicode_ci
 AND r.task_index_type = 'task_batch'
WHERE r.deleted_at IS NULL
  AND b.tenant_id = <当前租户>            -- 默认租户匹配 '' 与 'default'
  AND b.task_object IN ('process','config_file')
  AND b.status IN ('succeed','failed','partly_failed')
  AND b.created_at BETWEEN [start, end]
  [AND b.creator IN (creators...)]
  AND r.status NOT IN ('SUCCESS','IGNORED','INITIALIZING','RUNNING','NOTSTARTED')
ORDER BY r.created_at DESC, r.id DESC
LIMIT 120001                                   -- 扫描上限，超限报错要求收窄范围
-- 扩展筛选（5.7）与内存分页在此之后完成，并回填当前页的 common_payload
```

**为什么明细用 join 而不是先查批次 ID 再 IN 回查**：批次一条对应任务多条，join 才能一次拿到跨批次的全局有序结果；先取批次 ID 再分片 `IN` 回查会放大成多轮查询。join 以批次表为驱动表，`task_records` 侧仍能走 `idx_task_index`。

**链路收敛要点：**

- `task_step_records` **不参与**统计，也不改结构；
- 聚合查询只 `SELECT task_index, message, creator`，不读 `payload` / `common_payload`；
- 明细查询才读取 `common_payload`，且只解析 `ProcessPayload.CcProcessID` 一个字段；
- 跨业务视图**不允许**逐业务循环调用单业务接口拼装结果，必须一次查询内聚合。

### 5.3 接口契约

**2 个接口，均为跨业务统计，只按时间范围与人员过滤：**

```
POST /api/v1/config/task_batch/statistics                 → ConfigServer.TaskStatistics
POST /api/v1/config/task_batch/statistics/failure_tasks   → ConfigServer.TaskFailureTasks
```

- 两条 RPC 均带 `method_visibility = "INTERNAL,BKAPIGW"`，无 inner 绑定；
- 路径**不带 `biz_id`**：范围为当前租户全部业务，不判断用户业务权限；
- 两个接口**共用同一组基础筛选**（时间范围 + 人员多选）；失败明细在此基础上另支持
  扩展筛选与动态筛选选项，见 5.7（概览与图表仍只按基础筛选聚合）。

### 5.3.2 实现约束

1. **人员多选必须直查 `task_records`，不能走框架 store**：框架 `istore.ListOption.Creator` 是单值字段，不支持 `creator IN (...)`；逐人查询再合并会破坏分页与去重。因此新增了 `internal/dal/dao/task_record.go` 只读 DAO。
2. **明细的人员条件作用在 `task_batches.creator`**，聚合的人员分布则取 `task_records.creator`；两者当前一致（`builder.TaskInfo.Creator` = 登录用户）。
3. **`common_payload` 只在明细读取**：聚合不能为取 CC 进程 ID 扫这一列。
4. **软删除条件不能省略**：`task_records` 聚合扫描到自定义结构体时 GORM 不注入 `deleted_at IS NULL`，`StatusCount` 显式手写；`FailureDetail` 用 `Unscoped()` 关闭批次表软删除注入后，显式写 `r.deleted_at IS NULL`。
5. **join 排序规则必须对齐**：`CAST(b.id AS CHAR)` 与 `task_index` 比较时两端排序规则不一致会报 `Error 1267 Illegal mix of collations`，代码显式 `COLLATE utf8mb4_unicode_ci`。
6. **租户边界**：`ListRefs` 与明细 join 都强制按当前租户过滤；默认租户同时匹配 `tenant_id = ''` 与 `'default'`（历史数据两种写法共存）。

### 5.7 失败明细多维筛选（扩展）

在基础筛选（`time_range_start` / `time_range_end` / `creators`）之外，`TaskFailureTasks` 支持组合筛选，
并在响应中返回各维度可选项，供前端动态构建筛选条件。概览与图表接口不改变，仍只按基础筛选聚合。

#### 请求：`TaskFailureSearch`

| 维度 | 字段 | 方式 | 匹配规则 |
|---|---|---|---|
| 任务 ID | `task_ids` | 多选 | `task_records.task_id` 命中任一 |
| 创建人 | `creators` | 多选 | 任务操作人（`task_records.creator`），空值归 `-`；必须是基础 `creators` 的子集 |
| 执行状态 | `statuses` | 多选 | `task_records.status` 命中任一 |
| 业务名称 | `biz_names` | 多选 | CMDB 业务名；映射失败时接受业务 ID 字符串 |
| 业务 ID | `biz_ids` | 多选 | `task_batches.biz_id` 命中任一；非数字直接返回 `InvalidParameter` |
| 开始时间 | `start_time` | 单个 | 任务开始时间的**下界**：`start >= start_time`；需落在 `time_range` 内 |
| 结束时间 | `end_time` | 单个 | 任务结束时间的**上界**：`end <= end_time`；需落在 `time_range` 内且不早于 `start_time`；`end` 为空的行不命中 |
| 错误码 | `error_codes` | 多选 | `message` 解析出的错误码；`--` 表示无错误码 |
| 失败信息 | `failure_message` | 模糊 | 对展示用失败原因（`taskerr.Readable` 后文本）做大小写不敏感子串匹配 |

规则：

1. 同一维度内为 OR，不同维度之间为 AND，未设置（空数组 / 空串）的维度不参与过滤；
2. 扩展条件必须在基础范围内：`start_time` / `end_time` 需落在 `time_range_start`~`time_range_end` 之间（可与边界相等），
   `creators` 需为基础 `creators` 的子集（基础 `creators` 为空表示不限，此时不校验），否则返回 `InvalidParameter`；
3. 错误码、失败信息、时间都来自行内数据解析，与明细展示口径一致。

#### 响应：`filter_options`

`TaskFailureFilterOptions` 全部为 `Choice{id, name}`，由**基础范围**（未应用扩展筛选）的行集生成，
因此用户选择某个维度后，其他维度选项不会收缩。生成规则：

| 字段 | 来源 | 排序 |
|---|---|---|
| `task_ids` | 基础范围内最新的 500 个任务 ID（去重） | 字典序 |
| `creators` | 操作人去重，空值归 `-` | 字典序 |
| `statuses` | 失败任务状态去重 | 字典序 |
| `biz_names` | CMDB 业务名，缺失时回落业务 ID | 字典序 |
| `biz_ids` | `id` = 业务 ID，`name` = 业务名（缺失时回落 ID） | 业务 ID 升序 |
| `start_times` / `end_times` | 实际存在的日期，UTC `yyyy-MM-dd`（按天） | 日期升序 |
| `error_codes` | 解析出的错误码 | 固定首个 `--`（无错误码），其余按数值升序 |

`failure_message` 为自由文本，不返回选项列表。

#### 实现与限制

1. 错误码与失败原因需要解析 `task_records.message`，无法下推 SQL；为避免同一批数据被反复扫描，
   基础范围内一次取回轻量行（不含 `common_payload`），选项生成、扩展过滤与分页都在内存完成，
   行序沿用 SQL 的 `created_at DESC, id DESC`（保证分页稳定、超限时丢的是最旧数据、明细按最新失败优先）；
2. `common_payload` 只对当前页的任务 ID 回填（`ListFailurePayloads`），避免大字段全量扫描；
3. 基础范围行数上限 `maxFailureTaskRows = 120000`，超出返回 `InvalidParameter` 要求收窄时间范围；
   不静默截断，否则总数与筛选选项都会不完整；
4. 开始/结束时间选项按天生成（时间范围 ≤ 31 天，选项 ≤ 31 个），避免逐任务秒级时间戳把响应撑爆；
   `start_time` / `end_time` 是区间边界而非精确匹配（`start >= start_time`、`end <= end_time`），
   入参支持 `yyyy-MM-dd`、`yyyy-MM-dd HH`、`yyyy-MM-dd HH:mm`、`yyyy-MM-dd HH:mm:ss` 与 RFC3339；
   只给到某一段时，下界取该段起点、上界取该段末尾（如 `2026-11-20` 作上界等价于当天 23:59:59）；
5. 任务 ID 选项上限 `maxFailureTaskIDOptions = 500`（取最新），配合 4 后单次响应稳定在几十 KB，
   不会触达 config-server 调 data-service 时 gRPC 默认 4MB 接收上限。

## 六、性能与索引

### 6.1 数据量估算

单批次 N 个实例 → `task_records` N 行。统计只取失败任务（按失败率 5% 估算），不扫步骤表。

| 规模 | 30 天任务记录 | 需解析的失败行 | 评估 |
|---|---|---|---|
| 小（日均 1k） | 3 万 | 约 1.5 千 | ✅ 可接受 |
| 中（日均 1 万） | 30 万 | 约 1.5 万 | ✅ 可接受，建议加结果缓存 |
| 大（日均 10 万） | 300 万 | 约 15 万 | ⚠️ 需限时间窗（≤7 天）+ 缓存 |

内存控制：单分片 250 个批次，失败行上限 12 万，聚合只保留计数不保留明细。

### 6.2 索引现状

| 表 | 现状 | 对统计的影响 |
|---|---|---|
| `task_batches` | `idx_tenantID_bizID_ccProcessID (tenant_id, biz_id)` | 跨业务查询只能命中 `tenant_id` 最左前缀，`task_object` / `status` / `created_at` 走回表过滤。**建议后续补 `(tenant_id, task_object, created_at)`**（本期未加迁移） |
| `task_records` | `idx_task_index (task_index, task_index_type)`、`idx_status`、`idx_task_type` | `task_index IN (...)` 与 join 均可走 `idx_task_index`，够用 |
| `task_step_records` | — | 不参与统计，无需改动 |

### 6.3 降级策略（已实现）

1. 时间跨度 > 31 天 → 返回 `InvalidParameter`，提示缩小范围；
2. 批次 > 50000 → 返回 `InvalidParameter`，提示收窄时间范围（**不静默截断**，避免概览与明细口径不一致）；
3. 人员 > 500 → 返回 `InvalidParameter`；
4. 单分片失败行达 12 万 → 该分片结果截断并打 `logs.Errorf`，其余分片继续统计；
5. 时间窗内无批次 → 直接返回全零概览，不发起任务表查询。

### 6.4 未实现的降级

- 结果缓存（建议 30~60s，按 `tenant_id + 参数指纹`）；
- 行数超阈值时只返回概览、不返回分布图；
- 批次超限时优先返回概览、不返回明细。

## 七、数据保留与风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 任务表无清理机制 | 框架只清 etcd 结果，`task_records` / `task_step_records` 持续增长 | 本期限定时间窗；后续评估归档（按 `created_at` 归档/删除 90 天前数据），需单独评审 |
| 重试覆盖历史 | 失败原因只保留最后一次 | UI 文案说明"最终结果"；需要历史时查日志 |
| 历史数据兼容 | 改造前 message 无结构段 | 正则 `errorCode=` 兜底；仍无码则不计入错误码分布 |
| 维度不可索引 | 维度在 `mediumtext` JSON 中 | 只做批内聚合；不做"按进程 ID 跨月全量查询" |
| **跨业务数据越权** | 平台级视图不做业务权限判断 | 强制租户隔离；页面标注"平台运营视图"；必要时接口审计 |
| 错误码字典不完整 | 无完整 GSE 错误码中文描述 | 不建全量字典：未命中展示"未知错误码 + 原始失败原因"，按 `code` 聚合后逐步补文案 |
| 业务名称映射 | CMDB 调用失败会导致业务名空白 | 映射失败降级展示 `biz_id`，不阻断查询 |
| 统计非快照 | 状态计数与失败聚合是两次查询 | 按最终一致处理，必要时前端提示"数据存在秒级延迟" |

## 九、待评审确认清单

### 9.1 已确认

1. **失败判定**：排除法，`status NOT IN ('SUCCESS','IGNORED','INITIALIZING','RUNNING','NOTSTARTED')` 即失败（3.3）。
2. **明细筛选**：概览与图表只按时间范围 + 人员（多选）聚合；明细在基础范围之上支持
   任务 ID、创建人、状态、业务、时间、错误码、失败信息等扩展筛选，并返回动态筛选选项（见 5.7）。
3. **错误数量口径**：按失败实例（任务）去重，与概览"执行失败实例数"一致。
4. **人员分布**：固定 Top3，其余合并"其他"；空创建人归 `-`。
5. **执行实例总数口径**：用 `task_records` 计数（与明细同源），`task_batches.total_count` 仅用于批次列表展示。
6. **跨业务权限**：不设平台级独立接口，统计接口本身即跨业务，不判断业务权限，仅保留租户隔离。
7. **错误码来源**：`message` 的 `[BSCP-ERR]` 结构段，历史数据回退正则。

### 9.2 待确认

8. **耗时过长批次/任务是否需要单列**：`total_count - COUNT(task_records)` 这部分实例没有任务行，批次 `failed_count` 已计入。统计是否单列"任务未创建数"？
9. **成功率分母**：当前 `failure_rate = failed / total`（`total` 含未执行与运行中）。是否需要改成 `failed / (success + ignored + failed)`？
10. **错误码中文文案**：未命中时展示"未知错误码 + 原始失败原因"是否可接受？
11. **默认时间窗 7 天、最大 31 天**是否满足使用习惯？
12. **统计索引** `(tenant_id, task_object, created_at)` 是否随本期上线补迁移？
13. **明细是否需要导出**（CSV/Excel）？导出上限如何限制？
14. **是否需要结果缓存**（30~60s）以缓解刷新压力？
