### ID 空间利用率与断层归因

已消耗 11249 个 ID，存量仅 1561 条，约 86% 的 ID 空间已被删除或跳跃吃掉。

按业务分布中存在一段明显断层：`2018` 到 `9999` 这近 8000 个 ID 上没有任何存量行。
按月新建量数据定位到了成因：

```
| 2021-01 |             8 |    197 |   1837 |
| 2021-03 |            10 |   1548 |  10002 |   ← ID 从 2000 级跳到 10000 级
| 2021-04 |            27 |     89 |  10004 |
```

2021-03 期间 ID 从 2000 级直接跳到 10000 级，是一次**一次性的人为跳跃**
（多为环境合并或数据迁移时手工设置 `AUTO_INCREMENT`），并非常态化的消耗模式。

因此"ID 消耗跳跃式、不可外推"这个判断不成立——除去 2021-03 那次人为操作，
此后五年的 ID 消耗是平稳且可外推的。

### ID 消耗速率与预留基线余量

| 观察窗口 | ID 推进 | 年均消耗 | 8751 余量可撑 |
| --- | --- | --- | --- |
| 近 12 个月（2025-09 至 2026-08） | 11077 → 11248，约 172 | 约 172 | 约 50 年 |
| 近 5 年（2021-12 至 2026-08） | 10212 → 11248，约 1036 | 约 220 | 约 40 年 |

历史峰值出现在 2021-07 / 2021-08，月新建 190 / 191 条，那是 GSEKit 刚上线的爆发期。
即使按每月 200 条的峰值持续估算，余量也能撑 3.6 年，而 GSEKit 正处于下线过程中，
不可能回到该量级。

**结论：预留基线 20000 余量充裕，无需上调。** 设计中保留的基线上调路径与余量告警
作为兜底机制仍有价值，但不再是需要优先处理的风险项。

### `100605` 的第 2 条差异：已确认为迁移后新建

GSEKit `100605` 的 10 条明细显示，未迁移的第 2 条是 `config_template_id = 11211`，
名称 `yun`，`created_at = 2026-06-05 07:25:34`，创建者 `noahchi`。

该业务的迁移时间是 `2026-06-04 11:19`，**`yun` 比迁移晚了约 20 小时**。迁移执行时它还不存在，
因此这不是迁移缺陷。`100605` 至此完全解释：

| 类别 | 条数 | 明细 |
| --- | --- | --- |
| 迁移成功 | 8 | 10589、10590、10594、10595、10915、10983、10984、11012 |
| 草稿被跳过 | 1 | 11175 `include` |
| 迁移后新建 | 1 | 11211 `yun`（2026-06-05） |

**这暴露了一个运维缺口。** 已迁移业务在 GSEKit 侧仍可继续新建模版，新建的模版永远不会出现在
BSCP，标准运维流程引用它就会失败，且数据会持续漂移。ID 对齐无法覆盖这类漂移出来的记录——
它们在 BSCP 里根本不存在。这必须靠流程管控解决：已迁移业务在 GSEKit 侧应禁写，
或至少在页面上给出显著提示。

由于此项已归因为"迁移后新建"，原先关于"迁移静默跳过"的怀疑暂时解除。但迁移工具在
`continue_on_error` 打开时确实会静默跳过失败记录：

```200:205:bk-bscp/cmd/gsekit-migration/migrator/config_template.go
					if m.cfg.Migration.ContinueOnError {
						log.Printf("  Warning: insert template failed for config_template %d: %v", tmpl.ConfigTemplateID, err)
						continue
					}
					return fmt.Errorf("insert template for config_template %d failed: %w", tmpl.ConfigTemplateID, err)
```

后续批次迁移时建议关闭 `continue_on_error`，或在迁移报告中显式列出被跳过的模版清单，
避免同类差异需要事后逐个归因。

| 60 | `abcdef` | 2026-08-12 07:06:19 | 改名为 `abcdef-rname` 后又改回 |

两条的当前名称都与 GSEKit 一致（`abcdef` ↔ 11012、`noah` ↔ 10589），名字匹配均能命中，
**都不需要人工介入**。

由此得出一条执行纪律：**被改动记录清单必须在对齐执行的同一时点重新采集**，
不能沿用任何历史快照。工具的阶段 0 应当自行采集全量数据，不接受外部传入的清单文件。

### 改名回滚事件的分析价值

这次"改名后又改回"提供了一个关键验证，价值高于原本的改名样本本身：
它证明了 `updated_at > created_at` 这个判据会产生**假阳性**。

这 2 条记录现在都处于"被判定为改动过、但名称与 GSEKit 完全一致"的状态。如果设计上用
"被改动过"来推断"改过名"，它们就会被错误地送进人工确认清单；而实际上名字匹配能正常命中，
应当自动对齐。在 15 条被改动记录中，假阳性占 2 条，比例并不低。

因此判据的职责必须严格划分：

| 判据 | 职责 | 不能用来做什么 |
| --- | --- | --- |
| `creator = xiaolnwang` + biz 白名单 | 判定"是不是迁移产物" | 判定是否改过名 |
| `reviser <> creator` 或 `updated_at > created_at + 2s` | 缩小人工复核范围 | **判定是否改过名**（存在假阳性） |
| 名字在 GSEKit 对应业务下能否命中 | **最终裁决**：命中即自动对齐，未命中即需人工介入 | — |

名字匹配判定的是**当前状态**，不关心历史。改回去了就等于没改过，这个语义是正确的，
因为对齐要做的事就是把当前这条记录接到正确的 GSEKit ID 上。

### 关键修正：`^v\d+$` 格式判据失效

`100605` 的版本名明细揭示了一个必须修正的设计缺陷：

```
| 60 | abcdef | v107618,v107619,v20260812143153,v20260812143211,v20260812150614 |
| 61 | noah   | v104709,v104753,v20260812143238                                 |
| 62 | noahchi| v104750,v104752,v104754,v106801,v106804,v106806                 |
```

迁移工具写入的锚点版本名是 `v` 加 GSEKit `config_version_id`（6 位数，如 `v107618`）：

```255:255:bk-bscp/cmd/gsekit-migration/migrator/config_template.go
						revisionID, fmt.Sprintf("v%d", version.ConfigVersionID), version.Description,
```

但 BSCP 页面更新配置模版时填入的版本名是 `v` 加时间戳（14 位数，如 `v20260812143153`），
**同样匹配 `^v\d+$`**。

需要强调的是，服务端对版本名不做任何格式约束，它直接采用请求传入的值：

```1018:1018:bk-bscp/cmd/data-service/service/config_template.go
	spec.RevisionName = req.GetRevisionName()
```

`v<时间戳>` 只是前端的默认值，用户可以改成任意字符串。这意味着版本名格式既不能证明
"是迁移产物"，也不能证明"不是迁移产物"，**任何基于格式的推断都不可靠**。

因此原设计中"该模版名下是否存在 `^v\d+$` 格式的 `template_revisions` 行 → 判定是不是迁移产物"
这条判据完全失效：BSCP 自建模版天生就带这个格式的版本名。

修正方式：格式匹配只能用于**筛选候选**，判定必须以"解析出的数字能在 GSEKit
`gsekit_configtemplateversion` 中反查到、且反查到的模版 `bk_biz_id` 与 BSCP `biz_id` 一致"
为唯一依据。

实际不会产生误匹配——`20260812143153` 远超 GSEKit `config_version_id` 的量级
（当前最大约 10 万），反查必然失败并被跳过。但绝不能把格式匹配当作独立结论。

不建议用"数字位数"来区分（6 位 vs 14 位）：这是脆弱的启发式，且反查本来就是必须执行的步骤，
没有省略它的收益。

### 附带发现：每次更新都会新建一个版本

`UpdateConfigTemplate` 在更新配置模版时会无条件创建一条新的 `template_revision`：

```1042:1043:bk-bscp/cmd/data-service/service/config_template.go
	// 生成新的版本文件
	_, err = s.dao.TemplateRevision().CreateWithTx(grpcKit, tx, templateRevision, true, false)
```

新版本以"最新版本"为模板复制后覆盖字段，因此改名操作会在 `template_revisions` 留下
时间戳痕迹（虽然拿不到改名前的名称）。本次 14:31 到 15:06 之间的四次操作因此可被完整还原，
见第一节的变更事件表。

对设计的意义：迁移写入的锚点版本行**不会被后续更新覆盖或删除**，只会被追加的新行"淹没"。
因此版本回溯链的可靠性不受用户更新操作影响，只有显式删除锚点行才会失效。

### 不能按 ID 顺序对应（结论保留，先前给出的实例已撤回）

**撤回说明。** 本文档早期版本称 `5000079` 的映射为乱序（BSCP 54→11121、55→11120），
并把成因归结为"迁移遍历按 `template_name` 排序"。这两点都不成立：

- 迁移代码中读取模版的查询**没有任何 `ORDER BY`**，不存在按名称排序一说；
- 该"乱序"是推断结果而非实测——只验证了 55、56 的名称，ID 54 的名称从未查询过，
  仅由"剩下那条只能是 11121"倒推得出。若被改动清单中的 ID 记录有偏差，该推断即不成立。

在 ID 54 的名称查实之前，不应把它当作事实引用。核实 SQL 见第七节待补数据。

**但"不能按顺序对应"这个结论本身仍然成立**，依据是代码而非该实例：分页查询缺少
`ORDER BY`（见下），遍历顺序不由 `config_template_id` 保证。任何按位置配对的简化都可能
把两条记录换到对方的 ID 上，而两个 ID 都合法、不会报错，属于静默数据损坏。
对齐必须逐条走名字匹配或版本 ID 回溯。

### 新发现：迁移分页查询缺少 `ORDER BY`

核实上述成因时发现的既有缺陷：

```155:158:bk-bscp/cmd/gsekit-migration/migrator/config_template.go
			var templates []GSEKitConfigTemplate
			if err := m.sourceDB.Where("bk_biz_id = ?", bizID).
				Offset(offset).Limit(batchSize).
				Find(&templates).Error; err != nil {
```

`Offset` + `Limit` 分页却不指定排序，MySQL 不保证跨批次的结果稳定，可能重复返回部分行、
遗漏另一部分行。重复会撞 `(biz_id, name)` 唯一索引，在 `continue_on_error` 为真时被静默跳过；
遗漏则直接漏迁，无任何提示。

触发条件是单业务模版数超过 `batch_size`（默认 500，见 `etc/migration.yaml`）。
已迁移业务中模版最多的仅 64 条，存量迁移大概率未触发。但后续 104 个业务需先确认：

```sql
-- GSEKit 源库：找出模版数接近或超过 batch_size 的业务
SELECT bk_biz_id, COUNT(*) AS tmpl_count
FROM gsekit_configtemplate
GROUP BY bk_biz_id
HAVING tmpl_count > 100
ORDER BY tmpl_count DESC;
```

修复方式：补上 `Order("config_template_id ASC")`。同文件中查询版本的逻辑已正确使用
`Order("config_version_id ASC")`，仅模版这一处遗漏。
